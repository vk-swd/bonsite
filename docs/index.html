Overview

What

This project demonstrates a simple Node.js + GraphQL + Kafka + MS SQL backend service architecture. It will also include a basic observability stack with Prometheus and Grafana. I have chosen to build a simple bank statement generator service that would replicate a hypothetical operation flow of services involved in transaction data collection and its presentation, while providing minimal observability metrics of the system performance.

Why

The problem choice is driven by the tech stack — which I realize isn’t the ideal way to approach engineering — but the goal of this project is to support a job application. Despite being tailored around specific technologies, I hope it still demonstrates skills and patterns that are transferable to other domains.

How

The diagram on Pic.1 demonstrates basics of what system does.
It is very limited view of a front - backend system.
Client 1 uses front end to submit data to the server.
Server processes the submission through several stages and generates internal data as needed.
Client 2 or 1 can then retrieve relevant information including the one submitted by Client 1.

The server will be composed of a multitude of distributed sets of services
that will ensure data persistence, reliability and availability while
providing high throughput and low latency.
This is usually achieved by careful infrastructure planning and strategic
separation of concerns.
For a simple isolated case of statement generation the hypothetical system
will be composed of the components presented in the diagram on Pic.2. The basic principle of concern separation is to plan services in such a way that they block each other as little as possible and provide an execution pipeline that would allow maximise the magnitude of concurrent task execution.
The components I chose are:

  • GraphQL API - a server processing frontend requests. Many devices can connect the server side simultaneously with different queries and mutations. Having a distributed entry point will allow to route those requests to the appropriate services. Using GraphQL provides many benefits to frontend development like schema introspection, type safety, simpler versioning and more. Could be replaced with REST API but for convenience and presentation purposes GraphQL is used here.
  • Transaction handler - this is a representation of an infrastructure responsible for taking the transaction request, accepting it and coordinating the reliable storage of the transaction data.
  • Source of truith - this is a storage system of all the data that is created from the user activity. It can be represented as a single database in a small application. In production grade scalable and reliable systems it is common to separate storage based on the type of data. - Critical, high-frequency, low-latency data (e.g. account balances) may live in specialized stores optimized for performance. - Less critical or large-volume data (e.g. support logs, analytics, transaction notes) can be stored in more general-purpose systems. Dedicated services manage access to this data.
  • Statement generator - this is one of the hypothetical services I decided to implement. It handles data that can be optimised for querying and benefit from using a relational system with indexing like MS SQL server. This kind of data can also be delivered using a distributed messaging broker like Kafka and be made available to other services while providing a reliable temporary storage with very fast insertions.
  • Frontend - this is some device application used by hypothetical users, which can post a transaction and request a bank statement.

So putting together the assumptions the components I made earlier, The source of truth can be represented as a combination of:

  • Core database to store critical information about transactions
  • Kafka - it would provide a reliable way to store high vollumes of data long enough to be consumed by other services processing them.
  • MS SQL Server - it would provide a way to store data in a structured way, optimised for querying and reporting.
    • This extends the system flow representation to the diagram on Pic.3.

    Now, building such system is a complex task, especially with a production grade guarantees in mind. This demo is not meant for that. My intention is to explore a technology in a simple way. For this reason I have decided to cut some corners:

  • Client behavior will be generated.
    It means I am not going to make any device apps. Instead I will emulate two kinds of actions:
    1. Posting a transaction - can be automated by producing transaction requests between random users at random times.
    2. Requesting a bank statement - can also be automated by posting statement requests for random users and random time intervals.
  • There would be no transaction processor.
    But it's operation will be emulated by special kind of generated events in response to transaction requests. Those events will emulate transaction processing latency and will also output transaction results. Both of which would be useful in system monitoring.
  • Since there would be no transaction processor, neither will there be a dedicated database for latency critical data.
  • For more convenience (although it is a matter of preference), it was chosen to set up a minimalistiv web UI displaying some basic controls for processes implemented in this project.

  • There will be only one instance of Kafka and SQL Server.
    This project is meant to be run on a single machine. Although one could use Docker, tc, and/or other tools to emulate a distributed environment and configure the storage systems to demonstrate their robustness, those activities are beyond the scope of this project.
  • There will also be a single kafka consumer per service accessing the messages as it is not practical to run multiple consumers sharing same io resources. For the same reason single partition will be used for data storage as no parallel consumption will take place.
